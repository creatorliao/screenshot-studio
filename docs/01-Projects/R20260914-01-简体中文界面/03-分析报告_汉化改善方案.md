## 一、结论（标 → 本 → 药）

**标（现象）**：本地启动后界面恒为英文，且无论怎么切 URL、切浏览器语言，都看不到一个中文界面。

**本（根因）**：**简体中文译文齐备、语言路由也通，唯独 UI 渲染层从未接线。**

三个关键事实串起来就解释了一切：

| 层面 | 状态 |
|------|------|
| 译文（`messages/zh.json`） | ✅ 齐备，与英文 **135/135 键对齐** |
| 路由与语言协商（`i18n/routing.ts` + `middleware.ts`） | ✅ 生效，`Accept-Language: zh-CN` → `307 /zh`，`<html lang>` 正确 |
| UI 渲染（组件文案） | ❌ **0 处调用 `useTranslations`**，约 750 处英文硬编码 |

所以译文的唯一去向是：被 `NextIntlClientProvider` 序列化进 RSC 脚本 → 发给浏览器 → **没有任何组件读它** → 丢弃。
实测 `/zh` 页面的**可见 DOM 中文字符数为 0**，而 1546 个中文字符全部躺在脚本里。

**这是一个"半接线"的国际化**：路由层做完了，渲染层没做。它比"完全没做"更具迷惑性——
因为 `/zh` 能访问、`<html lang>` 也变了，看起来像支持中文，实际是空壳。

**药（方向）**：把 UI 渲染层接到已经存在的翻译体系上，并补上"选得了、记得住、跳页不丢"三件事。
**不需要重做 i18n，也不需要新写中文译文。**

### 一个反直觉但重要的判断

用户第一反应是"改默认语言参数"。**这是错误的第一反应**，理由：

- 该仓库是 `screenshot-studio.com` 的源码，`/` 既是编辑器入口，也是**当前唯一的 SEO 规范入口**（`app/layout.tsx:341` `canonical: "/"`，`app/sitemap.ts:17` `path: "/"` 优先级 1.0）。
- 把 `defaultLocale` 从 `en` 改成 `zh` 会让 `/` 变成中文，英文整体搬到 `/en/*`。**线上英文根路径的 SEO 权重会被搬走**，且已收录的 URL 语义全变。
- 而改 `defaultLocale` 对"用户看到中文"这件事**毫无帮助**——因为无论 `/` 还是 `/zh`，可见文案都是英文。改完只会让中文用户看到一个"URL 是中文、内容是英文"的 `/`。

结论：**`defaultLocale` 不是本次的必改项**，真正必改的是渲染层接线。

## 二、根因分析：为什么会变成"半接线"

不是单一 bug，是四处断点叠出来的复合缺陷：

1. **译文先行、接线未跟进**。`messages/*.json` 8 个语种 + `i18n/routing.ts` 一并提交，但组件改造没做。译文成了"孤儿资产"。
2. **语言切换入口缺失**，所以没有任何路径暴露"翻译没接线"这件事——用户根本进不到一个"应该是中文"的语境里，缺陷因此长期潜伏。
3. **`i18n/navigation.ts` 定义了却没人用**。语言感知的 `Link` 导出了，36 个文件仍直接 `import Link from "next/link"`。即使渲染层接好了，跨页跳转也会把语言丢掉。
4. **文档与实现对不上**。`ARCHITECTURE.md` 零 i18n 章节，但 `lib/agents/llms.ts:355` 对外宣称 "i18n: next-intl with 8 locales"；隐私政策还描述了一个实际不存在的 `NEXT_LOCALE` cookie 记忆功能。对外承诺跑在了实现前面。

这解释了为什么"看起来支持 8 语种"却"一个中文都没有"。

## 三、方案总览

| | 方案 A：打通链路 | 方案 B：全站汉化 | 方案 C：只改默认语言 |
|---|---|---|---|
| **做什么** | 修好渲染层接线 + 切换入口 + 导航/metadata 跟随语言，范围先覆盖**编辑器主界面与全站外壳**（导航/页脚/通用按钮） | A 的全部，再把 **750 处**英文全部接入，并补齐 6 个非中文语种 | 只把 `defaultLocale` 改成 `zh` |
| **用户能否看到中文** | ✅ 能（编辑器 + 全站框架） | ✅ 能（全站无死角） | ❌ **完全不能**，文案仍是英文 |
| **改动面** | ~30 文件 | ~206 文件 / 750 位点 | 1 行 |
| **工作量** | 3～5 人日 | 15～25 人日 + 翻译校对 | 0.1 人日（但无效） |
| **风险** | 低，可增量验证 | 中，回归面广 | 高（SEO 语义错乱），且零收益 |
| **建议** | ⭐ **推荐先做** | 后续按需推进 | **不做** |

方案 C 列在这里只为明确排除：它满足不了需求，还会带来 SEO 副作用。

## 四、推荐方案：方案 A，分四阶段推进

原则：**每一阶段结束都能独立验证、可随时停**。

### 阶段 1：打通链路，先让"一个中文句子"出现在屏幕上（0.5～1 人日）

先做最小闭环，用来证伪"接线是否真的可行"，避免一上来铺开 750 处。

1. **确认 Provider 有 messages**
   `app/[locale]/layout.tsx:36` 的 `<NextIntlClientProvider>` 未传 `messages`。
   next-intl v4 会从服务端 catalog 继承（实测 RSC payload 里确实有全量译文），**因此这一处可能无需改动**——但要**实测确认**，不能假设。若客户端 `useTranslations` 报 missing，则显式传：
   ```tsx
   const messages = await getMessages();
   <NextIntlClientProvider messages={messages}>
   ```

2. **挑一个客户端组件试点接入**
   建议从 `components/editor/EditorHeader.tsx`（17 处文案、编辑器最顶部、视觉最显眼）开始：
   ```tsx
   const t = useTranslations("editor");
   // "Undo" → {t("undo")}
   ```
   `messages/zh.json` 的 `editor` 段已有 `undo`/`redo`/`exportVideo` 等键，可直接用。

3. **验证**：访问 `/zh`，能看到"撤销""重做""导出视频"。

> 阶段 1 的产出是一个**可证伪的最小证据**。如果这一步不通，后面所有工作量都要重估。

### 阶段 2：补上"选得了、记得住、跳页不丢"（1～1.5 人日）

这一步解决需求 R2/R3，也是当前**完全空白**的部分。

4. **新增语言切换组件**（当前不存在，grep 无任何 `LocaleSwitcher`）
   建议 `components/i18n/LocaleSwitcher.tsx`，用 `@/i18n/navigation` 的 `usePathname` + `useRouter` 切换：
   ```tsx
   "use client";
   import { usePathname, useRouter } from "@/i18n/navigation";
   import { useLocale } from "next-intl";
   // router.replace(pathname, { locale: next })
   ```
   同时修掉 `i18n/routing.ts:16-25` 的 `localeNames`：把 `ja:"Japanese"`→`日本語`、`ko:"Korean"`→`한국어`，
   补 `Espanol/Francais/Portugues` 的变音符，并把 `zh` 显示为**「简体中文」**（而非 `Chinese`）。
   建议改为按当前语言本地化显示语种名，或用各语言的自称。

5. **把切换入口挂进导航**
   `components/landing/Navigation.tsx` 与 `components/editor/EditorHeader.tsx` 各放一个入口。

6. **把 36 处 `next/link` 换成语言感知 Link**
   `import Link from "next/link"` → `import { Link } from "@/i18n/navigation"`。
   涉及文件（实测 36 个）分布：
   - `app/[locale]/*/page.tsx`：约 20 个页面
   - `components/landing/*`：Navigation / Footer / Hero / Pricing / FAQ / FinalCTA / BackedBy / Sponsors / EditorPreview
   - `components/editor/*`：EditorHeader / CodeImagesBanner
   - `components/tools/ToolPage.tsx`、`components/ui/github-star-button.tsx`
   - 注意 `app/error.tsx`、`app/not-found.tsx` 在 `[locale]` 之外，需单独判断是否保留 `next/link`

   > 这是**当前最容易被忽略的坑**：不移交，从 `/zh` 点任意导航都会掉回英文，
   > 阶段 1-2 的成果会在用户第一次点击时全部失效。

7. **验证**：切到简中 → 跳 `/about` → 仍是中文（URL 应为 `/zh/about`）→ 关浏览器重开 → 仍是中文。

### 阶段 3：让页面标题也跟随语言（0.5～1 人日）

8. **metadata 接入 `getTranslations`**
   现状全站 metadata 是英文硬编码常量（`app/layout.tsx:238-393`，各 `app/[locale]/*/page.tsx`）。
   改为 `generateMetadata` + `await getTranslations({ locale, namespace })`。
   至少覆盖 `title` / `description` / `openGraph.title` / `openGraph.description`。
   否则浏览器标签页和分享卡片仍是英文——用户会觉得"汉化没做完"。

9. **修 `openGraph.locale`**
   `lib/seo/metadata.ts:14` 固定 `"en_US"`，应随语言变化（`zh_CN` 等）。

10. **验证**：`/zh` 的 `<title>` 为中文；社交分享预览为中文。

### 阶段 4：主界面高频文案铺开（1～2 人日）

11. 按 `02-调查` §3 的 Top 文件清单优先推进，重点是**编辑器实际会被点到的控件**：
    `CodeImageEditor.tsx`(35) → `editor-right-panel.tsx`(23) → `DepthSection.tsx`(20)
    → `ToolOptions.tsx`(18) → `overlay-controls.tsx`(18) → `EditorHeader.tsx`(17) → `MockupControls.tsx`(15)
    → `text-overlay-controls.tsx`(13) → `RightSettingsPanel.tsx`(12) → `TweetImportSection.tsx`(11)

12. 每接入一批就同步**补 `messages/zh.json` 的键**。现有 `editor` 段只有 12 个键，
    而编辑器实际需要数百个键——**译文扩充是本阶段真正的工作量所在**，不是改代码。

13. 建一个"漏翻看门狗"：next-intl 在缺 key 时会打 `MISSING_MESSAGE` warning，
    建议在开发期把该 warning 当失败处理，避免长期漂移回英文。

## 五、关键技术决策点

| # | 决策 | 我的建议 | 理由 |
|---|------|----------|------|
| **D1** | 是否改 `defaultLocale` | **不改，保持 `en`** | 改它会搬走线上英文根路径的 SEO 权重；且对"看到中文"零帮助。靠"协商 + 切换 + cookie"即可满足 R2/R3 |
| **D2** | 用 `zh` 还是新增 `zh-CN` | **先用现有的 `zh`** | 避免路由前缀与 8 个语种文件名连带改动；将来要分 `zh-TW` 时再引入 `zh-CN` 更划算 |
| **D3** | 切换后如何持久化 | **依赖 next-intl 的 `NEXT_LOCALE` cookie** | 顺带让隐私政策那句描述变成真的（当前是空头承诺） |
| **D4** | 非默认语言的 `noindex` 是否放开 | **本次保持现状**，另开需求 | `app/[locale]/layout.tsx:17-18` 的 `noindex` 更像刻意 SEO 策略，不该趁汉化顺手改 |
| **D5** | 中文字体 | **阶段 4 时再处理** | 27 个字体全是 `subsets:["latin"]`，中文会回退浏览器默认字体。可用 `font-family` 兜底链（如加 `"PingFang SC","Microsoft YaHei",sans-serif`）低成本解决，无需引入 CJK webfont |

## 六、风险与副作用

| 风险 | 说明 | 缓解 |
|------|------|------|
| **既有英文页面回归** | 把 `next/link` 换成语言感知 `Link` 会改变所有页面生成的 href | 逐页对比 href；`localePrefix:"as-needed"` 下英文页应保持无前缀 |
| **英文 SEO 受影响** | 引入 hreflang / 放开 noindex 会改变爬虫行为 | D4 明确本次不动 SEO；D1 不动 `defaultLocale` |
| **客户端 Provider 缺 messages** | 若 v4 的继承行为与预期不符，`useTranslations` 会报 missing | 阶段 1 第 1 步先实测，不通过就显式传 `getMessages()` |
| **译文扩充量大** | 750 处文案，`zh.json` 现有 135 键远不够 | 分阶段，不追求一次全站；编辑器优先 |
| **中文文案撑破布局** | 中文更短但标点/换行规则不同，按钮与标签可能溢出 | 阶段 4 每批改完目视检查关键控件 |
| **`localeNames` 被误用** | 当前写法有误且未使用 | 阶段 2 一并修正 |
| **改 `next/link` 影响非 `[locale]` 路由** | `app/error.tsx`、`app/not-found.tsx` 在 locale 段之外 | 单独判断，别无脑替换 |

## 七、明确不做的事

1. **不改 `defaultLocale`**（理由见 D1）——这是最容易被当成"解决方案"的伪解法。
2. **不重写中文译文**——`zh.json` 已与英文 135 键对齐，质量可用；只需**扩充新键**。
3. **不趁本次动 SEO 结构**（hreflang、sitemap 多语言、放开 `noindex`）——属独立决策，需单独确认。
4. **不一次铺满 750 处**——按阶段推进，每阶段可验证可停。
5. **不引入 CJK webfont**——用系统字体兜底链即可，避免大幅增加首屏体积。
6. **不修 `middleware` → `proxy` 的 Next.js 16 废弃警告**——与本需求无关。
