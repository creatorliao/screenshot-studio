## 1. 这份需求在说什么

原始笔记把三件不同的事写在同一段里。真正要交付的不是「若干篇介绍」，而是 **一套能完成「理解 → 学会 → 应用」的系列培训教程**。

| 层次 | 要做什么 | 不是什么 |
|------|----------|----------|
| 工作准备 | 在 `dev-creator` 分支上工作；用 PARA 把文档放进可维护的目录 | 不是改编辑器功能、不是发版 |
| 研究取证 | 从代码和文档抽出：作者意图、心智模型、功能、主流程、用法证据 | 不是凭印象或官网文案臆造 |
| 终交付 | 主题夹里的系列教程：先建立地图，再跟做，再独立应用 | 不是概念堆砌，也不是按源码目录翻译的 API 清单 |

一句话：**先从仓库取证，重建作者怎么设计这套工具；再按工作流写成可检验的培训系列。**

为什么要这样写：下一任智能体如果只拿到「写出教程」，往往会产出功能目录。学习者要的是会用、会判断、会换任务再做一遍。需求必须把学习结果写死，写作才不会走偏。

## 2. 背景与现状

- **产品**：浏览器里运行的开源截图编辑 / 样机（mockup）工具。无需注册，无水印。在线地址见仓库 README。
- **学习场景**：学习者面对的是一个完整源码仓库，不是安装包说明书。教程必须能把「界面上能做的事」和「仓库里能证实的事」对上，但正文仍面向使用，不把读者按进组件文件树。
- **仓库现状**：根目录已有 `README.md`、`CONTRIBUTING.md`。本培训项目已落在 `docs/01-Projects/R20260906-01-Screenshot-Studio-培训教程/`；系列教程尚未撰写。
- **缺口**：README 能说明「是什么、有哪些能力、怎么 `npm run dev`」，但没有作者工作流、没有可跟做的最短成功路径、没有「换一个任务自己做」的应用练习。

## 3. 学习目标（本需求最重要的一节）

培训成功，不以「写了多少篇」衡量，而以学习者三层能力是否达成衡量。

| 层次 | 学习者必须能做到 | 教程必须提供 | 如何检验 |
|------|------------------|--------------|----------|
| **理解** | 用自己的话说清：作者希望谁、用它解决什么问题；画面是怎么被「组成」再「导出」的 | 作者意图 + 一张心智模型（输入 → 画布合成 → 导出）+ 主流程与支线的关系 | 能不看界面，画出或复述这张模型，并指出自己现在走到哪一步 |
| **学会** | 沿着主路径独立完成一次「素材进 → 编辑 → 导出」；知道每个流程节点上有哪些功能、点哪里、看到什么 | 最短成功路径 + 按节点展开的操作步骤 + 「你应该看到什么」 | 按教程做，能导出一张与步骤描述相符的结果 |
| **应用** | 关掉教程，用一个新任务再走一遍（换素材、换画幅或换用途），并说得出自己做了哪些选择 | 每模块一道迁移练习；系列结束一道综合任务 | 新任务能出图；选择能用模型里的词解释（画幅、样机、背景、标注、导出规格） |

四条操作目标是上面三层的落地，不是另一套目标：

1. **可启动**：能打开线上版，或完成本地安装并进入编辑器。核心路径不被可选配置（R2、数据库、分析）挡住。
2. **可理解**：能说清作者意图、心智模型和一条主工作流。
3. **可操作**：按节点找到功能并做出来（上传 / 截网页 / 套样机 / 调背景 / 标注 / 导出等，以仓库证据为准）。
4. **可应用**：能换任务独立完成，而不是只会复述点击顺序。

作者侧的默认教学立场（写教程时保持这个声音，细节仍须仓库证实）：

- 这套工具是为了让产品截图、界面样机、代码图、推文卡片在浏览器里一次做完，不必先打开设计工具或付费 SaaS。
- 使用者应先想「这张图给谁看、用在哪」，再选画幅与样机，再调背景与标注，最后才选导出格式与倍率。
- 仓库是证据来源，不是教材目录。学习者先建立使用模型，需要时再下探到对应代码位置。

## 6. 取证研究（动笔前必须先完成）

分析对象是**当前这个仓库里的产品**，不是「截图工具」这个品类。每个结论都要能指回 README、页面文案、路由或实现代码。

执行智能体先交一份分析稿（可独立成篇），再开写教程。分析稿至少回答：

1. **作者希望谁、用来干什么？**  
   从落地页、功能页、编辑器默认态、导出能力反推目标用户与典型产出。只写仓库能证实的。

2. **心智模型是什么？**  
   用一张短模型概括产品内部逻辑，例如「获得画面 → 在画布上合成（样机 / 背景 / 标注 / 文字）→ 按规格导出」。模型里的每一格都要能对上界面分区或代码模块。

3. **有哪些功能？挂在模型的哪一格？**  
   按用户能感知的能力罗列（背景、浏览器样机、3D、标注、代码出图、推文出图、动画时间轴、导出等），注明入口（路由或编辑器分区），并标到心智模型的节点上。禁止只按文件名平铺。

4. **主路径与支线分别是什么？**  
   主路径：最普通的「截图/上传 → 美化 → 导出图片」。  
   支线：代码出图、推文出图、动画导出等。支线单独成课，不要和主路径搅在一节里。

5. **作为一个用户，第一次应该怎么走？**  
   何时用线上版、何时本地启动；打开后先做什么；哪一步会第一次看到「做成功了」。

6. **作者希望用户怎样决策？（工作方法）**  
   不是按钮清单。例如：先定用途与画幅，再选样机与背景，最后选导出。方法必须能从信息架构或默认工作流推出来。

7. **证据索引**  
   每个功能 / 流程节点对应：界面入口 + 关键文件路径。供教程附录「想继续看代码时看这里」使用。未证实的条目标为「未证实」，不得进入教程正文。

没有证据的条目不进入教程。官网宣传语只能当线索，必须回仓库核对。

## 7. 系列课结构（给下一任智能体的目录合同）

教程是系列课，不是百科。模块可以合并，但主题不可缺；顺序不要反。

| 序号 | 模块 | 这一课解决哪一层 | 读完必须能做到 |
|------|------|------------------|----------------|
| 00 | 学习地图 | 理解 | 说出作者意图、画出心智模型、知道后面各课对应模型哪一格 |
| 01 | 得到一份能运行的工具 | 学会（启动） | 打开线上版，或本地安装启动并进入编辑器；知道哪些配置可以先不管 |
| 02 | 最短成功路径 | 学会 | 不展开旁支，跟做一遍「素材进 → 导出一张图」 |
| 03 | 按主路径展开功能 | 学会 | 在「取画面 / 套样机 / 调背景 / 标注 / 画幅」各节点上，知道有什么、怎么用 |
| 04 | 支线能力 | 学会（按需） | 仅写仓库里真实存在的支线（如代码出图、推文出图、动画）；每条支线说明它从主路径哪里分出去 |
| 05 | 导出与用好 | 学会 → 应用 | 按用途选择格式与规格；用产品里已有的预设、草稿等能力，不编造技巧 |
| 06 | 综合应用 | 应用 | 关掉前面各课，完成一道新的综合任务，并用模型复盘自己的选择 |
| 附 | 卡住时看这里 | 学会 | 安装、环境变量、浏览器限制、导出失败等，以仓库实际为准 |
| 附 | 代码对照表 | 理解（可选深挖） | 模型节点 → 路由 / 模块路径；方便从使用下探到源码 |

00 可以很短，但不能省：没有地图，后面的操作课会重新变成按钮清单。  
06 不能省：没有新任务，学习者停在「跟着点过」，到不了「应用」。

## 8. 单课必须长什么样

每一课（00 的地图课、附录除外）按同一骨架写。智能体不得只写讲解、把练习留空。

1. **本课目标**：两到三句，写「读完能做到什么」，对应第 3 节的理解 / 学会 / 应用。  
2. **它在模型的哪一格**：用 00 课的心智模型定位，先讲作者意图，再讲界面。  
3. **跟做步骤**：编号；命令可复制；用产品里的真实用词；每组步骤后写「你应该看到什么」。  
4. **自检**：3～5 条，学习者能当场打勾（例如：我导出了一张 PNG；我能指出背景是在哪改的）。  
5. **迁移练习**：换一个素材、画幅或用途，不看步骤重做；写清任务、可用条件和「怎样算做成」。  
6. **证据**：文末列出本课结论对应的文件 / 路由。想看实现的人往下走；不想看的人可以停。

写作硬约束（来自原始需求，仍然有效）：

1. 从作者角度先讲「用来干什么」，再讲控件。  
2. 功能挂在工作流节点上，不按组件文件名或设置面板标题平铺。  
3. 用法写到可执行：点哪里、输入什么、期望看到什么。

4. 本需求与研究方案的正文在本主题夹；`docs/需求.md`、`docs/研究方案.md` 只保留指向本夹的指针，避免旧路径找不到稿。

### 步骤 B · 取证分析

1. 阅读 README、CONTRIBUTING、环境变量示例、应用内文案、主要路由与编辑器分区实现。  
2. 按第 6 节写出分析稿：意图、心智模型、功能挂载、主路径 / 支线、工作方法、证据索引。  
3. 把「已证实 / 未证实」分开。未证实的不写进教程正文。

### 步骤 C · 撰写系列课

1. 按第 7 节建目录（文件可以合并，主题不能丢）。  
2. 按第 8 节写每一课。  
3. 文风：先目标，再步骤，再「你应该看到什么」，再练习。简体中文；技术专有名词保留英文原文（如 PNG、WebP、FFmpeg、Next.js）。

### 步骤 D · 自检

对照第 10 节逐条勾选。缺证据的段落删掉或改回「仓库里找不到，故不写」。缺迁移练习的课补上再交付。

## 12. 约束与方法

- **证据优先**：结论来自文档或代码。官网宣传语只能当线索，必须回仓库核对。  
- **模型优先**：先有心智模型，再挂功能。没有模型不要开写操作课。  
- **流程优先**：目录跟着核心工作走，不跟着组件文件走。  
- **练习优先**：每课有自检和迁移；系列有综合任务。只讲不做，不算交付。  
- **确定优先**：步骤写死到可核对的结果；避免「可以试试」「或许」。  
- **PARA 分流**：进行中的需求 / 方案 / 教程进 Projects 主题夹；规范类进 Areas；外部摘录进 Resources；过期稿进 Archives。  
- **不拆散本项目**：需求、方案、教程只在本主题夹追加；`docs/` 根的指针文件不要改写成正文。
