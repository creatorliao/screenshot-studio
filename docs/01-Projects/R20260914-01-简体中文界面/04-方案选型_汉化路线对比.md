## 一、结论先行

**推荐「就地汉化」（AST 字典替换），不推荐给 2654 处文案套 hook 的经典 i18n 接线。**

一句话理由：**全站有 50% 的文案住在动态数据结构里，这是所有 hook 方案的死穴，而就地替换能 100% 覆盖且几乎不改变代码结构。**

| 方案 | 覆盖 2654 处 | 结构风险 | 构建风险 | 工作量 | 结论 |
|------|--------------|----------|----------|--------|------|
| A 经典 `useTranslations` + 语义键 | 需重构 1339 处数据结构 | 高 | 高 | 很大 | ❌ 不推荐 |
| B `useExtracted`（官方实验特性） | **做不到** | 高 | 高 + 实验特性 | 大 | ❌ 不推荐 |
| **C 就地汉化（AST 字典替换）** | **✅ 100%** | **极低** | **近零** | 中等（主体是翻译） | ⭐ **推荐** |
| D 只改 `defaultLocale` | ❌ 0% | 无 | 无 | 1 行 | ❌ 无效 |

## 二、精确工作量（AST 清点，非估算）

用 TypeScript AST 对 `app/` + `components/` + `lib/` + `hooks/` 做上下文感知清点
（剔除 Tailwind 类名、`cn()` 调用、URL、slug、常量名、metadata `keywords`）：

| 指标 | 数值 |
|------|------|
| 扫描源文件 | 320 |
| **用户可见文案位点** | **2654** |
| **去重后独立文案** | **1945** |
| 去重后英文总字符 | 77,298 |
| 涉及文件 | 165 |

按来源通道拆分——**这是本次选型的关键数据**：

| 通道 | 数量 | 占比 | 说明 |
|------|------|------|------|
| JSX 文本节点 | 746 | 28% | `<button>Export</button>` 这类 |
| JSX 文本属性 | 218 | 8% | `placeholder=` / `title=` 等 |
| JSX 表达式字符串 | 351 | 13% | `{cond ? "Yes" : "No"}` 这类 |
| **数据对象属性** | **1339** | **50%** | 模块顶层的数组/对象数据，如 changelog、FAQ、Pricing、presets |

> 清点脚本：`scripts/i18n-inventory.ts`，明细：`i18n-inventory.json`

### 清点过程中的两次自身纠错（说明数据可信）

1. **v1 高估 4 倍**：把 `className={cn("flex items-center...")}` 里的 Tailwind 类名当成文案，
   扫出 5042 条，其中 4065 条是误报。
2. **v2 漏掉一半**：只认 JSX 形态，漏掉模块顶层的普通对象数据
   （如 `const offerings = [{title: "100+ Backgrounds"}]`、`lib/seo/comparisons.ts`），
   而这些最终都会被渲染成界面文字。v3 补上后从 1307 涨到 2654。

**结论：任何"拍脑袋估 750 处"的判断都不可靠，必须先 AST 清点。**

## 三、为什么 hook 方案在这里行不通（决定性论据）

### 3.1 `useExtracted`（方案 B）根本覆盖不了这 50%

我核查了本机实际安装的 next-intl 4.13.0 与官方文档：

- `useExtracted` 是**官方标注的实验特性**，需在 `createNextIntlPlugin` 里开 `experimental.extract: true`。
- 它的键是**编译期自动生成的哈希**（官方示例 `t('Look ma, no keys!')` → 键 `VgH3tb`），
  由 SWC 插件（`next-intl-swc-plugin-extractor`，WASM）做**静态分析**生成。
- 源码印证：`MessageExtractor.js` 里 `source.includes('useExtracted')` 才解析，
  本质是对源码做静态字符串提取。

**静态提取无法处理 `t(item.title)` 这种动态键**——而 1339 处（50%）正是这种形态。
它们要么被漏掉，要么必须把数据结构整体重构，等于方案 B 的核心卖点（免造键）直接失效。

参考：[useExtracted (experimental) 官方文档](https://next-intl.dev/docs/usage/extraction)

### 3.2 经典 `useTranslations`（方案 A）能跑，但代价与风险不成比例

它在**运行时**支持动态键，所以技术上能覆盖那 1339 处。但代价是：

1. 把每一个数据对象属性从 `title: "100+ Backgrounds"` 改写成 `titleKey: "about.backgrounds"`，
   再到渲染处 `t(o.titleKey)`——**1339 处数据结构重构**。
2. 手工造 **约 1945 个语义键**，并同时维护 `en.json` 与 `zh.json`。
3. 给 165 个文件加 hook。其中大量是 `"use client"` 组件、也有 RSC 组件，
   混用 `useTranslations` / `getTranslations` 需要逐个判断上下文，极易出错。

三点叠加，改动面与回归风险都远超收益——而用户要的只是"界面是中文"，
不是"支持多语言"。

## 四、推荐方案 C：就地汉化（AST 字典替换）

### 4.1 做法

1. 我产出一份 `英文原文 → 简体中文` 的翻译字典（约 1945 条）。
2. 写一个 **AST codemod**（TypeScript Compiler API，非正则），
   按字典精确替换字符串字面量，**只改字符串内容，不改任何代码结构**。
3. 保留 next-intl 骨架与 `messages/*.json` 原样（不删除、不破坏）。
4. `defaultLocale` 设为 `zh`，使根路径 `/` 直接就是中文。
5. 构建 + 运行验证。

### 4.2 为什么它更优

| 维度 | 表现 |
|------|------|
| 覆盖率 | ✅ 2654 处统一处理，包括 hook 方案够不着的那 50% |
| 结构风险 | ✅ 几乎为零：不引入 import、不加 hook、不改数据结构、不动 server/client 边界 |
| 构建风险 | ✅ 仅字符串内容变化，语法结构不变 |
| 漏翻降级 | ✅ 字典里没有的字符串保持英文——与任何方案的实际降级效果相同 |
| 可回退 | ✅ 配合 `git` 可整体回退；另存英文原文快照便于比对 |
| 工作量 | 中等，且**主体是翻译本身**（任何方案都省不掉） |

### 4.3 必须接受的代价（一次性说清）

1. **应用变成中文单语言**。切到 `/en` 也不会回到英文（因为英文原文已被替换）。
2. **next-intl 骨架闲置**：`i18n/*`、`middleware.ts`、`messages/*.json` 仍在，
   但不再影响界面文案。这是"留而不废"，不是坏味道，但确实是冗余。
3. **与上游合并冲突变大**：165 个文件被改动。考虑到本仓库已在 `dev-creator` 分支上分叉，
   这个代价基本已经付过了。

### 4.4 明确不汉化的范围（汉化反而会坏功能）

| 范围 | 原因 |
|------|------|
| `lib/constants/fonts.ts` | 字体族名必须原样传给 canvas / CSS |
| `lib/constants/aspect-ratios.ts` | `16:9` 之类非语言内容 |
| `lib/api/openapi.ts` | OpenAPI 规范，给开发者/机器读 |
| `lib/agents/**` | `llms.txt` 等面向 AI 抓取的内容，保持英文 |
| metadata `keywords` | SEO 关键词，非用户可见 |
| `className` / `cn()` / URL / slug / 常量名 | 非文案，清点时已剔除 |

## 五、执行计划（方案 C，供确认）

| 步 | 内容 | 产出 |
