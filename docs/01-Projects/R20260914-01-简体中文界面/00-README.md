## 一句话结论（调查阶段）

**简体中文译文是齐的（`messages/zh.json` 与英文 135/135 键对齐），语言路由也是通的
（实测 `Accept-Language: zh-CN` → `307 /zh`），唯独 UI 渲染层从未接线
（全仓 0 处 `useTranslations`，约 750 处英文硬编码）。**

因此 `/zh` 页面的**可见 DOM 中文字符数为 0**——中文只存在于 RSC 序列化脚本里，没有任何组件读它。
施工前**不存在任何让用户看到中文界面的办法**，换 URL、切浏览器语言都不行。

这是"半接线"的国际化：路由层做完了，渲染层没做。

## 关键提醒（调查阶段结论，对方案取舍仍然有效）

1. **改 `defaultLocale` 是错误的第一反应** —— 前提是**渲染层不接线**。
   若渲染层不接线，它既不能让你看到中文，又会把线上英文根路径 `/` 的 SEO 权重搬到 `/en/*`。
   本项目最终选择了"就地汉化 + 同时把 `defaultLocale` 改为 `zh`"，因为渲染层被直接改成了中文，
   前提条件已经不成立。
2. **36 处 `next/link` 的语言感知问题**在本方案下不再是问题（因为不再依赖 locale 前缀切换文案），
   但若日后要真接 next-intl，这条仍然成立。
3. **不需要重写中文译文** —— 现有 `messages/zh.json` 可作起点；本次是就地替换硬编码，未使用它。
